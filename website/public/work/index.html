MOHAMUD MOHAMUD / AI AGENT ENGINEERING

I built the computer around the model.

Aether is an autonomous-agent runtime I built independently over nine months to understand what makes capable models succeed or fail when they have to do real computer work.

It is not a wrapper demo. Aether runs tasks, gives models tools and computer access, preserves state, recovers from failures, separates model/runtime/evaluator faults, records evidence and subjects completion to independent review.

01 / WHAT I BUILT

A real agent runtime, not a prompt chain.

The core design problem was simple: let the model own strategy, while the runtime makes tools, state, action, recovery and evidence dependable enough for long-running autonomous work.

AGENT LOOP

Model-led execution.

The model sees the observed world, chooses actions, changes course and decides what capability it needs next. The runtime executes rather than silently replacing the model's strategy.

TOOLS + COMPUTER

Capability with boundaries.

Files, terminal actions, computer interaction, extensible tooling and task-environment bridges operate inside explicit execution boundaries instead of hidden evaluator access.

CONTEXT + STATE

Keep the work coherent.

Useful state, observations and evidence survive across long tasks and recovery instead of relying on a fragile single-shot prompt.

RECOVERY

Failures become state.

Tool, provider, environment and validation failures are made observable so the model can react rather than the harness silently retrying away the evidence.

VERIFICATION

Independent review, not a second strategist.

A read-only completion reviewer can challenge evidence without becoming sovereign over task strategy. Official grading remains outside the agent.

EVAL + PROVENANCE

Know what actually happened.

Run records, trajectories, runtime identity, evidence hashes and qualification receipts preserve enough lineage to audit successes, misses and invalid runs separately.

02 / FAILURE ENGINEERING

The interesting part is what breaks.

One Aether task was externally graded as a pass while the internal verifier still blocked completion after repeated path-boundary failures. That distinction mattered: the artifact was correct, but the review path was wrong.

Another held-out task failed while an out-of-workspace action was correctly rejected. That is a task loss and a boundary success at the same time. Treating those as one number would hide the engineering lesson.

That is how I work on agent systems: preserve the exact failure, identify which subsystem owned it, change only what the evidence supports, then rerun under controlled conditions.

ENGINEERING PRINCIPLE

Make failures legible.

A capable agent is not just one that succeeds. It is one whose failures leave enough reality behind to recover, debug and improve the system.
