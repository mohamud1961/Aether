At that point the conversation remains stuck in RUNNING , even though provider access and sandbox startup are already confirmed healthy. Expected behavior After the first successful model completion, the agent should continue normally by emitting one or more of: assistant event tool/action event observation event The agent loop should progress instead of stalling. Actual behavior Observed behavior: sandbox starts successfully repository preparation completes conversation reaches READY first LLM completion succeeds conversation stays in RUNNING event stream contains only early startup events and the user message no assistant/action/observation events follow Why this looks important This is not a basic provider or startup failure. In our environment, the following were already confirmed healthy at the time of this failure: self-hosted app server was running sandbox container was alive repository root layout had already been corrected locally provider route through LiteLLM was working direct provider completions were working the first agent-side LLM completion was recorded in conversation stats So the failure seems to happen after a valid model response is obtained, somewhere in the transition from model output to persisted agent/runtime events. Observed state Conversation-level observations: status remained RUNNING runtime status reached READY conversation stats showed a successful model completion the persisted event log contained only: system prompt event user message event state update events But no assistant/action/observation events appeared afterwards. Impact This makes the self-hosted agent effectively unusable even when: the provider is working the sandbox is working the repository is available It turns the remaining failure into an opaque runtime/debugging problem. Notes We are happy to provide a more minimal reproducer or sanitized event/log excerpts if that would help. The main value of this report is that it isolates a likely V1 runtime bug beyond the earlier startup/configuration issues.
