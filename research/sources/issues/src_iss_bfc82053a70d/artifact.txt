Important and should be addressed in the near term. Description JaykumarGirase11 opened on Mar 9, 2026 Issue body actions What would you like to be added? Currently, the glob and grep (ripgrep) tools in Gemini CLI do not expose any user-configurable limit on the number of results returned. On large monorepos or deeply nested codebases, both tools silently truncate their output when internal limits are hit — with no warning to the user or the agent that results are incomplete. Specific gaps found in source code: In packages/core/src/tools/ripGrep.ts, the tool has a hardcoded internal cap on output size via summarizeToolOutput(). There is no max_results parameter in the tool's JSON schema (GREP_DEFINITION in coreTools.ts), so the agent has no way to request fewer results or paginate. Similarly, packages/core/src/tools/glob.ts returns all matching paths up to an internal truncation threshold with no user-facing control. What should be added: An optional max_results parameter (integer) on both glob and grep/ripgrep tool schemas — defaulting to current behavior but allowing the agent or user to override When results are truncated (either by the new limit or the existing internal cap), the tool response should explicitly state: "Results truncated at N matches. Use max_results or a more specific pattern to refine." — instead of silently cutting off A global setting in settings.json under toolConfig to set a default maxGlobResults and maxGrepResults for the entire session — useful for monorepo users who always want tighter limits Why this matters: When the agent runs grep on a large codebase and gets silently truncated results, it makes decisions based on incomplete data — leading to missed matches, wrong edits, and subtle bugs. The agent has no way to know results were cut off, so it cannot self-correct or retry with a narrower query. This directly impacts agent reliability on real-world large projects. Why is this needed? On large monorepos and enterprise codebases, both glob and grep tools silently truncate results when internal limits are hit. The agent receives no signal that its output is incomplete — so it proceeds with confidence on partial data, leading to: Agent makes wrong decisions silently When grep truncates results mid-way, the agent believes it has found all occurrences of a pattern. It then proceeds to refactor, rename, or delete — missing the files that were cut off. The user discovers broken code only after the fact. No self-correction is possible Because the truncation warning is buried inside summarizeToolOutput() in packages/core/src/utils/summarizer.ts and returned as part of the raw LLM content string — not as a structured error field — the agent cannot programmatically detect that results were incomplete. A proper is_truncated: true flag in the tool response would allow the agent to retry with a narrower pattern automatically. Users have no way to tune performance Power users on large repos want to set max_results: 20 for exploratory queries to get faster responses. Currently there is zero control — every glob and grep runs to the internal limit with no way to opt for speed over completeness. Silent truncation breaks the trust contract The core promise of an AI coding agent is that it operates on accurate, complete information. Silent truncation violates this — the agent confidently acts on an incomplete picture of the codebase with no indication anything is wrong. An explicit truncation signal restores honesty between the tool layer and the model. Additional context Relevant source code locations (verified in repo): packages/core/src/tools/ripGrep.ts — no max_results parameter exists in the tool schema. Output is passed through summarizeToolOutput() which truncates silently. packages/core/src/tools/glob.ts — similarly returns all matches with no configurable cap and no truncation signal in the response. packages/core/src/tools/definitions/coreTools.ts — both GREP_DEFINITION and GLOB_DEFINITION schemas have no max_results field defined. Adding it here would automatically expose it to the agent. packages/core/src/utils/summarizer.ts — this is where truncation currently happens silently. A one-line addition of is_truncated: true in the return object would fix the self-correction problem immediately. Real world impact scenario: Monorepo: 800+ files, 150k lines of code Agent task: "Rename all usages of getUserById to fetchUserById" Agent calls grep("getUserById") grep internally hits limit, returns 47 matches, silently drops 23 Agent renames all 47 occurrences confidently 23 files still have old name — build breaks Agent has no idea why build is broken User spends 30 min debugging what the agent broke Proposed schema change (minimal, backward-compatible): typescript// In GREP_DEFINITION and GLOB_DEFINITION { name: "max_results", type: "integer", description: "Maximum number of results to return. Defaults to 100.", optional: true } // In tool response { results: [...], total_found: 70, // actual count before truncation returned: 50, // count actually returned is_truncated: true // agent can detect and retry } Related settings.json addition: json{ "toolConfig": { "maxGrepResults": 50, "maxGlobResults": 100 } } This would give monorepo users session-wide control without needing to specify max_results on every single tool call.
