In deployments using S3, GCS, or webhook-based file stores, a crafted pickle payload in the state file could achieve remote code execution on state restore. Affected code openhands/controller/state/state.py:167,175 — State restoration: encoded = file_store . read ( get_conversation_agent_state_filename ( sid , user_id ) ) pickled = base64 . b64decode ( encoded ) state = pickle . loads ( pickled ) # No validation openhands/server/services/conversation_stats.py:85 — Metrics restoration: pickled = base64 . b64decode ( encoded ) self . restored_metrics = pickle . loads ( pickled ) # No validation Why this matters The FileStore abstraction supports multiple backends (S3, GCS, local, webhooks). In cloud deployments: A misconfigured storage bucket with write access would allow an attacker to replace the state file with a malicious pickle payload The payload executes on the next restore_from_session() call — no user interaction required The SaaS code path (lines 169-175) has the same vulnerability in its fallback This is different from the intentional exec() / subprocess usage in the runtime — those are the product's core functionality. Pickle deserialization in state management is an incidental attack surface. Suggested fix Replace pickle with a safe serialization format. Options: JSON + dataclass conversion (safest): Serialize State fields to JSON, reconstruct on load RestrictedUnpickler : Allow only State , Action , Observation classes HMAC signing : Sign the pickle payload on save, verify before loads() Option 1 is recommended since it eliminates the deserialization attack surface entirely.
