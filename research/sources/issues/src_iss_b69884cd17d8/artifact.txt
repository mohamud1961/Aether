This causes auto-compaction to trigger prematurely even when actual context usage is well below the threshold. Evidence In a day of normal usage (2026-02-12), 13 of 14 auto-compaction events were false alarms : Memory flush prompt fired (writing daily notes, sending "compacting..." message) But totalTokens stayed flat or increased after the flush Only 1 event showed an actual token drop (real compaction) Example token breakdown on a typical turn: input: 3, output: 115, cacheRead: 7842, cacheWrite: 166635 totalTokens computed as ~174k (near 200k limit) Actual context usage: ~118 tokens Sessions that previously lasted 7+ hours before compaction were compacting every 11-33 minutes after large tool results inflated cache token counts. Root Cause In src/agents/usage.ts , derivePromptTokens() sums input + cacheRead + cacheWrite for the prompt token count. This is then used by deriveSessionTotalTokens() to set totalTokens , which the auto-compaction threshold checks against. Cache tokens ( cacheRead , cacheWrite ) represent API-level prompt caching accounting, not actual context window consumption. They should not be included in the context usage calculation that drives compaction decisions. Additional Issue After auto-compaction occurs, totalTokens is not refreshed from the (now smaller) session state. The stale pre-compaction value persists, which can cause repeated compaction triggers even after successful compaction. Fix Change derivePromptTokens() to use input + output only (exclude cacheRead and cacheWrite ) After auto-compaction, estimate tokens from the compacted session file and update totalTokens Environment OpenClaw v2026.2.9 Model: Claude Opus 4.6 (200k context) Anthropic API (prompt caching enabled) Reactions are currently unavailable Metadata Metadata Assignees No one assigned Labels No labels No labels Type No type Fields Give feedback No fields configured for issues without a type.
