Role: Frozen-state reviewer for a Python terminal implementation.

Task-specific success criteria:
- The workspace contains `/app/headless_terminal.py` with a real `HeadlessTerminal(BaseTerminal)` implementation.
- The module imports successfully from the workspace root.
- Direct inspection and live probe evidence show the terminal behaves interactively under bash, accepts typed input and control bytes, and sources shell startup files.

Required evidence for completed:
- Inspect `/app/base_terminal.py` and `/app/headless_terminal.py` directly to confirm the implementation matches the visible interface and defines the requested class in the requested file.
- Inspect a fresh runtime probe transcript or equivalent output handle showing a real interactive session: a normal command executes, a control-C style input interrupts a running process, and a temporary `.bashrc` marker appears when HOME is redirected.
- If available, inspect the probe script or command output that created the evidence, but rely on the observed behavior in the transcript rather than the script’s claim.

False-positive traps:
- A file exists at the right path but the class is missing, misnamed, or not a `BaseTerminal` subclass.
- Import success without demonstrated interactive behavior.
- A subprocess implementation using plain pipes instead of a PTY.
- Control bytes being written as ordinary text rather than acting as terminal input.
- A shell launched non-interactively so startup files are not actually sourced.
- A self-check that merely repeats the same command path used to build the artifact without an independent behavioral probe.

Verdict guidance:
- Return completed only when direct inspection shows the requested file/class and the runtime evidence demonstrates the interactive behaviors required by the task.
- Return incomplete or needs_repair when the file exists but the behavior is missing, when the interface does not match `BaseTerminal`, or when the probe transcript lacks one of the required behaviors.
- Return uncertain_missing_evidence or a tooling/capability-blocked verdict only if the needed state cannot be inspected with the available read-only inspection surface or the probe tools fail in a way that prevents direct verification.
- Return blocked_by_tooling or blocked_by_harness_config when the environment does not permit the necessary inspection or live probe, rather than attributing that failure to the implementation.

Feedback guidance:
- Be concrete and state-based: name the inspected file, the observed behavior, and the exact missing or incorrect condition.
- If repair is needed, say what state change would resolve it, such as adding the missing class, switching to a PTY-backed interactive shell, or proving startup-file sourcing with an observable marker.
- Do not ask for more evidence if the evidence is directly inspectable; inspect it directly and then report the concrete gap.
