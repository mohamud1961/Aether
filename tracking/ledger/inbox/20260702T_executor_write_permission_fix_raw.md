- summary: Two consecutive VM runs (full Stage 1 rerun and a cheap openssl-only retry) hit an identical, deterministic PermissionError on /tmp/tbench_openssl-selfsigned-cert_*/check_cert.py at kernel step 0. Root cause confirmed empirically (not just theorized): the task workspace is bind-mounted into a long-lived Docker container that runs as root; the solver's run_command actions execute via docker exec inside that container, so a shell command creating/writing a file at a path SubprocessExecutor.write_file later targets leaves that file root-owned on the host. A subsequent host-side open(path, "w") then raises PermissionError even though the harness process owns the enclosing workspace directory, because overwriting existing file CONTENTS requires write permission on the file itself (owner/group/other bits), not the directory. Reproduced the exact failure with a minimal docker-exec-then-host-write test, then confirmed a remove-then-write fix works (deleting a directory entry only requires write permission on the PARENT directory, which the harness always owns, sidestepping the ownership mismatch without chmod/chown, which would themselves fail on a file this process doesn't own).
